一个翻译单元里塞进三种 API 风格、九个工具、多代理编排、跨进程消息总线、 加密凭据保险库、路径沙箱与提示注入防御。本文不从功能清单开始，而是从 这些功能分别解决了哪一类结构性问题开始。

一、四层骨架

把一个可用的 Agent 拆开看，它大致由四层组成。层与层的区别不在于依赖顺序， 而在于它们各自回答什么问题。

层回答的问题代表机制详见
控制平面一次对话如何开始、被叫停、被续接、被压缩？代理循环、中断状态、上下文压缩、按目录会话设计的解读 第九节
能力平面模型如何动手，且多个执行体不互相踩脚？工具注册表与两段式调度、read-before-edit、Teamwork、通知总线设计的解读 第四、七、八节
信任平面"能动"如何不等于"可为所欲为"？沙箱模式、路径门禁、人工确认、注入清理、凭据保险库设计的解读 第十节
底座协议与 I/O 上有哪些只有跑起来才会撞的坑？SSE 增量解析、流式索引上界、原子写入、输入归一化设计的解读 第二、三、十一至十四节

四层里，控制平面和信任平面决定了系统是否"能上线"，能力平面决定了它是否 "有用"，底座决定了它是否"不会半夜崩掉"。一个只做了能力平面的 demo 是玩具； 一个只做了信任平面而没有控制平面的系统，会在用户按 Esc 时丢失整轮对话。

这份骨架也解释了为什么 cell.cpp 值得作为样本：它把四层都做了，而且明确 标注了哪些是刻意的取舍、哪些是明说的局限。

二、控制平面：让一次对话可以被叫住

2.1 循环本身没有上限

代理循环的终止条件不是"最多 N 轮"，而是模型在某一轮不再发起工具调用、 工具被拒绝、用户取消或发生错误。这看似简单，但它决定了系统不能对长任务做 提前截断——而这正是编码代理和问答代理最大的行为差异。

代价是必须有别的机制来接管"提前结束"。cell.cpp 用两条路径覆盖它。

2.2 中断是一种状态，不是一次异常

用户按 Esc，模型可能已经吐了半段文本、半个工具调用。朴素的处理是丢弃整轮， 但那会让长任务前功尽弃。cell.cpp 的处理是把它当作一个可持久化的状态：

  1. 已完整到达的 token 原样保留，截断到最后一个完整流事件——不会补全，也不会 补造半个字符；
  2. 仍在发出的工具调用被整体丢弃，因为它的参数通常是截断的 JSON，留着会让 下一次请求对每个 provider 都变成非法的（有 tool_call 没有对应结果）；
  3. 追加一条 system 消息说明原因，让模型知道上一轮为什么停；
  4. 状态写进会话目录下的 interrupt.json，重启后仍可恢复。

/reload 随后只做一件事：把现状 transcript 原样再发一遍。partial reply 和 中断说明已经在里面了，所以它不注入任何新内容——这恰好保证了模型是在接续， 而不是在重新开始。

值得单独一提的是 Anthropic 的 thinking 块需要签名才能重放。中断在思考中途 产生的无签名块会被丢弃，有签名的保留。这不是过度设计，而是一个真实的 协议约束被提前想到了。

2.3 压缩是显式动作，不是自动降级

触发条件有两个：上下文溢出报错时压缩一次并在同一轮内重试（不计作失败尝试）； 以及长时间工具密集型轮次后自动压缩。两者走同一个 compact() 路径。

几个细节体现了"显式"的思路：每条消息先拆成对话文本与推理两部分、各截断到 400 字符，分别送给压缩模型（可以用与聊天模型不同的模型），两份摘要再合成一条 system 消息；最近一条用户消息被保留——因为只含 system 消息的对话会被很多 聊天模板直接拒绝（No user query found in messages），留着它压缩结果才至少 能撑起一次真实轮次。

压缩前会先把完整 transcript 归档到 saved/msg-<time>.jsonl。归档失败就不压缩。 这个顺序保证了压缩永远不会导致数据丢失。

2.4 会话是一个目录，不是一个数组

会话 id 是 <cwd-key>-<unix-millis>-<8 hex>，cwd key 是规范化工作目录 SHA-256 的 前 16 位。每个会话是一个文件夹，里面放着 messages.jsonl、teamworks.json、 interrupt.json、notices/ 和 saved/。

这个选择的收益是恢复路径是确定的：切换会话直接跟随它的 cwd，不需要额外的 映射逻辑；删除会话就是删目录，不会有孤儿记录；压缩归档和中断状态天然与会话 同生命周期。

配套的写入策略是合并 + 原子替换：按路径合并提交，后台线程落盘，每次写入先写 <name>.tmp、刷到存储设备、再 rename 覆盖。崩溃永远不会留下一个被下次启动 静默读成空的截断文件。 flush() 是真正的持久性屏障——/save、/session、 /compact 和退出路径都会先调它。

三、能力平面：让"能动"不等于"乱来"

3.1 Policy 与 Phase 是两个正交维度

一次助手消息里可能有多个工具调用。cell.cpp 把它们拆成两个 pass：

  • Pass 1（并发）：所有只读工具（ls / read / rg / find）提交到共享 线程池并发执行；
  • Pass 2（顺序）：write / edit 必须等所有读完成，exec 需要确认， tw 会阻塞等待子代理。

关键在于把两个维度分开建模：Policy（Deny / Ask / Allow）回答"能不能跑"， Phase（Concurrent / Deferred）回答"什么时候跑"。混成一个枚举，之后每加一个 工具都要重新定义组合语义。

结果始终按原始 tool_call 顺序写回 transcript，因为模型期待结果与请求同序。

3.2 read-before-edit：把模型的不确定性挡在文件之外

编辑工具最常见的失败模式不是权限被拒，而是模型凭训练记忆编造文件内容， 然后去 edit 一个并不存在的字符串。cell.cpp 的解法是记录每一次 read 返回的 行范围，edit 前检查目标行是否落在已读区间内：

  • 读过 [1,10] 和 [20,30] 之后编辑第 15 行会被拒绝，尽管两个范围都记录了；
  • 可见上下文一变（/clear、/new、/session、/compact），日志就清空—— 之前那次读在模型眼前已经不存在了；
  • 从带行号的 read 输出里复制搜索块必然带尾随换行，但文件可能没有，所以有一条 "去掉换行重试"的分支。

这条约束把"模型必须先看"从提示词里的建议变成了工具层的硬约束。

3.3 子代理编排：阶段、门控与文件租约

Teamwork 允许主代理创建作业，子任务可以组织成命名阶段的工作流：阶段顺序 执行，阶段内串行或并行；并行走共享线程池（上限 thread_pool_size，默认 16）， 而不是每个子代理一个 std::async。

三个设计值得单独说：

后台运行必须在池外。 /teamworks run_bg 起专用 runner 线程，因为并行阶段 会把 worker 提交到池里再阻塞等待——runner 若在池中就会死锁。池托管的运行 永远不死锁，退出时 join。

Gate 是流程节点，不是确认弹窗。 带 gate: true 的阶段结束后作业转为 waiting 并发通知，监督者审查报告后再 run 恢复。这让"人在回路"成为工作流 里一个自然的阶段，而不是散落各处的特殊分支。

文件租约把所有权做成了显式规则。 子代理始终可以创建新文件（创建即归属）， 但改动已存在文件需要主代理在 editable 里显式授权，且必须同时给出 edit_rules。每一次对授权文件的修改都会触发一次监督审查——一次独立的 LLM 请求，携带路径、工具参数、文件当前内容和即将产生的结果，要求模型回复 批准或拒绝。

审查是 fail-closed 的：缺失或失败的审查一律拒绝，绝不静默放行。被拒的子 代理会拿到裁决和原因作为工具结果，可以修正后重试（每个子代理最多 8 次审查）。 租约锁在发出审查请求之前就释放，所以多个子代理的审查互不排队。

3.4 零 token 的等待是一个特性

监督者需要知道子代理进度，但轮询会烧 token。cell.cpp 的 notice 总线让等待 变成零成本的原子操作：

  • 发送方把 JSON 文件原子写入目标会话的 notices/pending/；
  • 进程内发送通过条件变量立即唤醒，跨进程发送靠约 0.7 秒的目录重扫发现；
  • /notices wait 阻塞在条件变量上，空闲时不发出任何 LLM 请求；
  • 待处理通知还会在每次 LLM 轮次前自动排空，所以监督者永远不必主动轮询。

还有一个容易被忽略的安全决定：通知 id 来自文件名而不是文件内容。如果 id 来自 JSON，恶意发送者可以写 "id": "../../../victim"，排空时的删除操作就被引到 了 pending/ 目录之外。用文件名做 id，路径穿越在构造上就不可能。

四、信任平面：诚实地说明"不做什么"

4.1 沙箱只管路径，而且明说了

cell.cpp 的 check_exec 只做两件事：拒绝 .. 遍历，拒绝引用敏感路径 （/.crypt、/.key、/config.json、/sessions/、/logs/）。它不解析命令名， 不解码 base64 载荷，也不阻止网络出口——python3 -c "exec(base64…)" 当然能 跑。

README 的 Implementation notes 专门有一段讲这件事：

The sandbox is path-only: box::check_exec / box::check do not parse command names, decode encoded payloads, or block network egress by binary name.

这种诚实是有价值的。很多安全文档会暗示"我们阻止了网络出口"，实际只是过滤了 几个命令名——那种承诺比没有承诺更危险，因为它让人以为可以少问一次。

真正的威胁模型是：不可信的代理运行在可信的主机上，命令由用户确认（或在 autoallow 模式下由 LLM 决定），沙箱负责的是防路径逃逸与防意外泄密。 六层 防线叠起来才构成防御深度：沙箱模式 → 路径门禁 → 人工确认 → 高风险二次确认 → 输出加固 → 凭据保险库。

4.2 注入防御：先归一化，再匹配

exec 的输出里可能嵌着"ignore all previous instructions"。朴素字符串匹配会被 轻松绕过：下划线连接、多余空格、西里尔字母 і、零宽空格、跨行拆分。

cell.cpp 的做法是先把每行归一化成规范 ASCII 再匹配：全角折成半角、 Latin-1 重音折回基本字母、西里尔/希腊同形字折成 ASCII 近似、删除零宽与双向 标记、标点折成空格。再把最多 6 个相邻行拼成窗口跑一遍，捕捉跨行拆分。

两道便宜的优化让它不至于拖慢正常路径：每个指纹和正则都要求至少命中一个词干 （ignor / disregard / overrid），只有命中词干才进正则；跨行窗口也只在有 词干提示时才拼。

除此之外还有一层包装：wrap_tool_output 给每个结果套上带工具名和路径标记 的显式不受信任边界标签，正文中任何伪造这个闭合标签的尝试都会被转义——注入内容 无法伪造嵌套的"已授权"工具块。

注意扫描只作用于 exec 结果（以及从磁盘重载的带 exec 标记的结果）。其他工具 在调用时已被沙箱判定为可信，只获得大小上限。这是刻意的取舍：扫描是有成本的， 不能无差别施加。

4.3 凭据：让 fail-closed 成为默认行为

.cell/.crypt 是 JSON 信封，含随机 base64 盐和每键的 {nonce, ct}。AEAD 密钥 用 Argon2id 从 CELL_VAULT_PASSPHRASE 或自动生成的 32 字节 .cell/.key 派生；有 AES-NI 时用 AES-256-GCM，否则透明回退到 XChaCha20-Poly1305。 明文存放在 sodium_malloc 缓冲区里，销毁时清零，比较是常量时间的。

自测里有一条断言专门检查明文不出现在保险库文件中。这类"失败模式要显式"的 选择贯穿全篇：审查失败即拒绝、上下文溢出走压缩而不是报错退出、配置解析失败 用默认值并继续而不是拒绝启动。

五、底座：只有跑起来才会撞到的坑

这一层的知识点密度最高，也最难靠"读文档"获得。它们分散在 设计的解读 的第二、三、十一至十四节，这里只列结论。

5.1 SSE：用游标，不要 erase

流式解析用 std::generator 做零拷贝事件生成器，缓冲区只追加， consumed 游标记录已消费位置，只有游标超过 64KB 时才真正删前缀。每秒几百个 chunk 的响应下，buf.erase(0, n) 是 O(n²)。

游标的代价是缓冲区可能无限增长（服务器不发换行符），所以设了 32MB 硬上限， 超过就抛异常，由 write callback 的 catch 转成 CURLE_WRITE_ERROR，干净收尾。

另外，[DONE] 哨兵前的 \r 必须在比较前剥掉——SSE 允许 CRLF，不剥就永远匹配不上。

5.2 流式索引由服务器控制

OpenAI 的流式 tool call 和 Anthropic 的 content block 都带 index。一个恶意的 （或有 bug 的）服务器可以发 index: 999999999。直接用它扩容数组，内存就没了。

cell.cpp 的防御是一个常量：kMaxStreamSlots = 128，超出的 delta 直接丢弃。 同时修了一个语义错误——索引缺失意味着"当前调用"，而不是"一个新调用"：

这个 bug 曾经让某些 provider 的每个 delta 都新建一个调用，最后拼出二十个残缺的 tool call。服务器输入永远是不可信的——这条原则在这里体现得最直接。

5.3 原子替换的细节

写 <name>.tmp → 刷盘 → rename。rename 失败会先删目标重试一次，再失败才回退 到直接写（Windows 上文件被占用时 rename 会失败）。

flush() 里有一个值得记的 bug 类型：in_flight 最初是 bool，而 worker 线程 和调用 flush() 的线程都会写它——先完成的那个会清掉标志，让 flush() 在还有 写入在途时就返回。计数型状态需要的是"减到零"而不是"置否"。

5.4 输入归一化的三个例子

数字参数。 LLM 经常把数字写成字符串（{"offset": "85"}）。解析时必须显式 拒绝负号（strtoull("-1") 不报 ERANGE，它会返回 ULLONG_MAX），并且要求 end 到达字符串末尾而不是 *end == '\0'——JSON 字符串可以内嵌 \0， "12\0 999" 会被错误接受成 12。

正则缓存。 rg / find 有一个 64 项的 LRU 缓存。最早返回 const std::regex&， 在并发下是未定义行为——另一个线程在匹配过程中触发 rehash 或淘汰，引用就悬垂。 返回 shared_ptr<const std::regex> 才正确。

系统消息折叠。 严格的 Chat Completions 模板只接受恰好一条 system 消息且 在最前面，而代理会在会话中途注入 system 消息（通知、技能、中断说明、压缩摘要）。 fold_system_messages 把它们按顺序合并成唯一的前导消息，在三个地方调用： 注入后、加载技能后，以及每次请求前的最后一道防线。最后一道防线是必要的， 因为 transcript 可能从磁盘加载，旧版本写的位置可能不规范。

这一节四个例子的共同点：每一个都对应一个真实的失败模式，没有一个是"以防万一"。

六、七条可推广的原则

从上面四层里能提炼出的、比实现更耐用的东西：

  1. 边界要物理隔离。 只有 cell::plat 知道 OS API，只有 cell::net 知道 curl，只有 cell::encrypt 知道 libsodium。跨平台、换库、安全审计都变成局部 问题——这是单文件约束最直接的收益。

  2. 不要为了统一而统一。 三种 API 各自实现客户端，在调用层分派。强行抽象成 最小公分母，会在每个 API 的边界上制造 bug（Responses 的 function_call_output 是顶层 item，Anthropic 的 tool_result 是完全不同的 block 类型）。

  3. 服务器输入是不可信的。 流式索引有上界、SSE 缓冲区有上界、正则有长度和 形状限制（拒绝 (a+)+ 这类指数回溯）、数字参数有符号和终止检查。

  4. 失败模式要显式。 fail-closed 不是口号，是每个分支的默认行为：审查失败 即拒绝，压缩前必须先归档成功，配置解析失败用默认值并继续。

  5. 持久化是状态机的核心。 会话、配置、Teamwork 存储、通知、中断状态各有 明确的磁盘表示与原子写入路径。崩溃后能恢复的不只是数据，还有状态机的位置。

  6. 诚实比承诺更重要。 沙箱是路径的就说路径的。README 专门用一节列出代码与 文档的差异、工具描述可能与实现漂移的地方。

  7. 零 token 的等待是特性，不是优化。 让"等待"成为零成本的原子操作，整个多 代理编排的形态都会随之改变——监督者可以放心地挂在那里直到有事发生。

七、动手清单

如果你准备自己写一个 Agent，下面这些是本文认为不能省的部分，按优先级排列：

  • 流式响应的缓冲区要有上界，消费要用游标而不是 erase；
  • 服务器给的流式索引要夹紧到常量上界，并且区分"索引缺失"与"索引为零"；
  • 编辑工具要维护已读行区间，覆盖不到的行直接拒绝，并告诉模型去读哪里；
  • 中断要保留已完整到达的部分，丢弃未完成的工具调用，并把原因写进对话， 而不是只打印到终端；
  • 上下文压缩前先归档原文，失败就不要压缩；压缩结果要至少保留一条真实用户 消息；
  • 工具调度把审批策略和执行时机分成两个维度；
  • 注入过滤要先归一化（同形字、零宽、全角、跨行）再匹配，并且要有便宜的 词干预过滤；
  • 凭据落盘要加密，明文缓冲区要显式清零，并且写一条断言检查明文没泄漏；
  • 所有文件写入走临时文件 + 原子替换，flush() 计数用"减到零"而不是布尔；
  • 从外部读回的字符串（路径、数字、id、正则）一律按不可信处理；
  • 并行执行的 worker 不要放回它们正在等待的那个池里；
  • 文档里写清楚系统不做什么，以及每个"不做什么"背后的威胁模型假设。

最后一条最容易被跳过，也最容易在半年后变成事故的根源。
