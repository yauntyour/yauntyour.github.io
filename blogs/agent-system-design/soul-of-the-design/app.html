cell.cpp：一个单文件 C++26 AI Coding Agent的设计哲学

Yauntyours·2026 年 10 月 11 日·4385 字·阅读 11 分钟

一个 8000 行的翻译单元里，藏着一个完整的 AI Coding Agent：三种 API 风格、九个工具、多代理协作、跨进程消息总线、加密凭据保管库、路径沙箱、提示注入防御——全部在同一个 .cpp 文件里。

为什么是"单文件"？

现代 AI Coding Agent（Claude Code、Cursor、Aider）几乎都以 Python 或 TypeScript 的形态出现，几百个文件、几十个依赖。cell.cpp 选择了相反的方向：一个翻译单元，两个系统库（libcurl + libsodium），一个 header-only 的 JSON 库。

这不是为了炫技。单文件带来几个真实的收益：

  • 构建 = 一行命令。g++ -std=c++26 -O2 -o cell cell.cpp -lcurl -lsodium。没有 CMake，没有包解析，没有虚拟环境。
  • 依赖方向是强制的。既然都在一个文件里，那就在物理上限制谁可以碰 OS API、谁可以碰 curl、谁可以碰 libsodium。答案是：只有 cell::plat、cell::net、cell::encrypt 可以。
  • 阅读即理解。从上到下读一遍，就理解了整个系统。

这个文件用命名空间把上万行代码组织成严格的层：

依赖是单向的：llm 依赖 net，teamwork 依赖 tools 和 chat，box 依赖 plat 和 text。没有环形依赖，没有全局状态。

一、三种 API，一种抽象

OpenAI Chat Completions、OpenAI Responses、Anthropic Messages——这三种 API 的请求体、消息格式、工具定义、流式事件各不相同。cell.cpp 没有把它们抽象成"最小的公分母"，而是各自实现一个客户端类，然后在调用层做分派。

这个决定的关键在于不做错误的统一。Responses API 的 function_call 和 function_call_output 是顶层 item，不是嵌套在 message content 里；Anthropic 的 tool_use 和 tool_result 是完全不同的 block 类型。如果强行用同一套 message 结构，就会在三个地方同时出错。

所以 cell.cpp 让每个客户端自己决定如何把内部 transcript 转换成自己的 wire format：

  • OpenAI::sanitize_messages() 把 reasoning 数组拍平成字符串，把 Anthropic 遗留的 tool_result 转成 role:tool 消息；
  • OpenAIResponses::convert_input() 把 tool call 提到顶层，把 tool 结果变成 function_call_output，把图片从 function_call_output 里拆出来放到下一个 user item；
  • Anthropic::body() 把 system 消息抽出来单独成字段。

内部 transcript 的表示是面向持久化的——它必须能被写进 JSONL、被重新加载、被三种 API 各自理解。这是一个双向约束，任何一端的 bug 都会在另一端暴露。

二、SSE 解析：零拷贝 + 增量游标

流式响应是 AI 客户端的核心路径。cell.cpp 用了一个 std::generator 做零拷贝的 SSE 事件生成器：

关键设计是 consumed 游标，而不是 buf.erase(0, n)。每个 chunk 到来时追加到缓冲区，解析器从上次游标继续，只在游标超过 64KB 时才真正删除前缀。这样避免了 O(n²) 的缓冲区搬移——一个高频的流式响应可能每秒产生几百个 chunk。

但游标有代价：如果服务器永远不发换行符，缓冲区会无限增长。所以设了 32MB 的硬上限，超过就抛异常，异常通过 write callback 的 catch 转成 curl 的 CURLE_WRITE_ERROR，干净地终止传输。

另一个细节：[DONE] 哨兵。SSE 允许 data: [DONE]\r\n 这样的 CRLF 结尾，如果不在比较前剥掉 \r，[DONE] 就永远不会被识别。

四、工具调度的两个 pass

一次 assistant 消息可能包含多个 tool call。cell.cpp 把它们分成两个 pass：

Pass 1 — 并发：ls、read、rg、find 这些只读工具提交到共享线程池，并发执行。

Pass 2 — 顺序：write、edit 必须等所有读完成（read-before-edit 规则），exec 需要用户确认，tw（Teamwork）会阻塞等待子代理。

这个设计有两个正交的维度：Policy（Deny/Ask/Allow，管审批）和 Phase（Concurrent/Deferred，管调度）。把两者分开是因为它们回答不同的问题：Policy 回答"这个工具能不能跑"，Phase 回答"什么时候跑"。

结果始终按原始 tool_call 顺序写回 transcript——LLM 期待的结果顺序和请求顺序一致。

五、read-before-edit：一个被低估的约束

编辑工具最常见的失败模式是：模型根据训练数据里的记忆编造文件内容，然后 edit 一个不存在的字符串。

cell.cpp 的解法是记录每一次 read 返回的行范围，编辑时检查覆盖：

edit 在替换前调用 read_covers(path, first_line, last_line)，任何未覆盖的行都拒绝编辑，并告诉模型去读哪些行。

这个机制还有几个细节：

  • 行范围会合并检查：读取 [1,10] 和 [20,30] 后编辑第 15 行会被拒绝，即使两个范围都记录了；
  • 文件末尾没有换行时，end == (size_t)-1 表示"到文件末尾"；
  • /clear、/new、/session、/compact 都会重置日志，因为上下文已经变了；
  • edit 的 search block 从编号 read 输出复制过来时必然带尾部换行，但文件可能没有——所以有一个"重试去掉换行"的分支。

六、提示注入防御：扁平化后再匹配

sanitize_output 是整份代码里最复杂的函数之一。它面对的威胁是：exec 命令的输出里嵌入"ignore all previous instructions"，被 LLM 当成新的系统指令。

朴素的字符串匹配会被轻松绕过：

  • ignore_all_previous_instructions（下划线连接）
  • ignore all previous instructions（多余空格）
  • іgnore（西里尔字母 і）
  • ignore\u200Bprevious（零宽空格）
  • 跨行拆分

七、Teamwork：子代理编排

Teamwork 允许主代理创建"作业"（job），每个作业包含一组子代理任务，可以组织成命名阶段（stage）的工作流。

关键设计：

阶段顺序执行，阶段内并行或串行。并行阶段提交到共享线程池（上限 thread_pool_size），而不是每个子代理一个 std::async。后台运行则在专用 runner 线程上执行——因为并行阶段会把 worker 提交到池里然后阻塞等待，如果 runner 本身在池里就会死锁。

Gate 是暂停点。带 gate:true 的阶段结束后，作业状态变成 waiting，发一条 notice 通知监督者。监督者审查报告后 run 继续。这让"人在回路"成为一个自然的流程节点，而不是一个特殊的确认弹窗。

文件租约（file lease）。子代理可以自由创建新文件（创建后归它所有），但修改已存在的文件需要主代理授权：

每次修改授权文件都会触发一次监督审查——一次单独的 LLM 请求，把路径、工具参数、文件当前内容、将要写入的内容和 edit_rules 一起送过去，要求模型回复 APPROVE 或 DENY。审查失败即拒绝（fail-closed），绝不静默放行。

租约锁在审查前释放，所以多个子代理的审查是并发的，不会排队。

多 provider。每个子代理可以有自己的 provider/model/think 等级。一个研究阶段用便宜的模型扫描，实现阶段用贵的模型打补丁。每个子代理构建自己的 LLM 客户端并在所有轮次复用，所以并行子代理之间不共享 curl handle。

八、Notice：零 token 的消息总线

Teamwork 的监督者需要知道子代理的进度，但轮询会烧 token。

cell.cpp 的方案是文件系统 + 条件变量的混合：

  • 发送方把 JSON 文件原子写入目标会话的 notices/pending/ 目录；
  • 进程内发送通过 condition_variable 立即唤醒等待者；
  • 跨进程发送通过 700ms 的文件夹重扫发现；
  • /notices wait 阻塞在条件变量上，不产生任何 LLM 请求。

等待期间进程完全空闲。子代理完成时唤醒，监督者审查报告，决定下一步。

notice 的 ID 来自文件名，不是文件内容——这是一个安全决定。如果 ID 来自 JSON 内容，恶意发送者可以写 "id": "../../../victim"，drain 时就把删除操作引到 pending 目录外。用文件名做 ID 意味着路径穿越在构造上就不可能。

九、中断与 /reload

Esc 取消流式响应时，模型可能已经输出了一半文本、一半 tool call。

cell.cpp 的持久化策略：

  1. 完整到达的 token 原样保留。SSE 解析器只应用完整事件，所以累积的文本总是停在 token 边界上。
  2. 未完成的 tool call 直接丢弃。它的参数通常是截断的 JSON，从未被批准或执行，也没有结果。留在 transcript 里会让每个 provider 拒绝下一次请求（有 tool_call 没有 tool_result）。
  3. 追加一条 system 消息记录中断原因。这是会话的一部分，不只是控制台输出——模型需要知道上一轮为什么停了。
  4. 中断状态持久化到 interrupt.json，进程重启后仍能 /reload。

/reload 什么都不注入，直接把 transcript 再发一遍——因为 partial reply 和中断通知已经在里面了。如果这次又中断了，状态就用新原因刷新。

还有一个容易忽略的细节：OpenAI 的 reasoning 块需要签名才能重放。中断在 thinking 中途产生的无签名 thinking 块会被丢弃，但有签名的会保留。这不是过度设计——Anthropic 在 tool call 前要求完整签名的 thinking 块，否则拒绝请求。

十、沙箱：诚实地说"不做什么"

cell.cpp 的沙箱是纯路径的，代码和 README 都明确说了这一点。

check_exec 只做两件事：

  1. 拒绝 .. 路径穿越；
  2. 拒绝引用敏感路径（/.crypt、/.key、/config.json、/sessions/、/logs/）。

它不解析命令名，不解码 base64 载荷，不阻止网络出口。

README 的"Implementation notes"章节专门讨论了这一点：

The sandbox is path-only: box::check_exec / box::check do not parse command names, decode encoded payloads, or block network egress by binary name.

这是有价值的诚实。很多安全文档会暗示"我们阻止了网络出口"，但实际上只是过滤了几个命令名，python3 -c "exec(base64...)" 轻松绕过。cell.cpp 选择说清楚：威胁模型是不可信的代理运行在可信的主机上，命令由用户确认（或 autoallow 模式下的 LLM 审查），沙箱负责的是防止意外的凭据泄露和路径逃逸。

真正的防线是分层的：

  • 沙箱模式：read-only 完全禁止 exec；
  • 路径门禁：阻止凭据文件、.cell 运行时目录、.. 穿越；
  • 人工确认：exec 是唯一的 Ask 工具；
  • 高风险二次确认：rm -rf、chmod、git commit 等需要第二次确认；
  • 输出硬化：exec 结果过注入扫描；
  • 凭据保管库：Argon2id + AES-256-GCM，sodium_malloc 缓冲区，析构时清零。

每一层单独都不够，但叠起来就形成了一个合理的防御深度。

十一、异步 I/O：原子替换 + 合并写入

会话、配置、统计的写入都走 async_io::file_writer：

  • 按路径合并：同一个文件在一秒内被写 10 次，只有最后一次落盘；
  • 后台线程：不阻塞主循环；
  • 原子替换：写 <name>.tmp → fsync → rename。崩溃或断电时，读者只能看到完整的旧文件或完整的新文件，绝不会看到截断的文件。

write_file_atomic 的 rename 失败时会重试一次（先删除目标），再失败才回退到直接写。Windows 上文件被锁定时 rename 会失败，这个重试是必要的。

flush() 是真正的持久化屏障：它等待所有 pending 和 in-flight 的写入完成。这里曾经有一个微妙的 bug——in_flight 是 size_t 而不是 bool，因为 worker 线程和调用 flush() 的线程都会写它。用 bool 的话，先完成的那个会清掉标志，让 flush() 在还有写入在途时就返回。

十二、系统消息折叠

这是一个为 llama.cpp 的 Jinja 模板做的妥协，但它暴露了一个通用问题。

严格的 Chat Completions 模板要求恰好一条 system 消息，且在数组最前面。但 cell.cpp 会在会话中途注入 system 消息：notice、加载的 skill、中断通知、压缩摘要。

解法是 fold_system_messages：把所有 system 消息按顺序合并成一条，放到最前面。

这个函数在三个地方被调用：注入 notice 后、加载 skill 后、以及每次请求前的最后一道防线。最后一道防线是必要的，因为 transcript 可能从磁盘加载——一个旧版本写的 transcript 可能有不规范的 system 消息位置。

Anthropic 和 Responses 客户端不在乎这个（它们本来就会把 system 消息抽出来），所以折叠只可能有益。

十三、数字参数的防御性解析

LLM 经常把数字写成字符串：{"offset": "85"}。如果直接 j["offset"].get<size_t>()，会抛 type_error。

num_arg 处理这个：

几个细节：

  • 显式拒绝负号：strtoull("-1") 不会报 ERANGE，它会把值取反成 ULLONG_MAX。所以符号必须手动检查。
  • end 必须到达字符串末尾：JSON 字符串可以内嵌 \0，strtoull 会在 \0 处停下，"12\0 999" 会被接受成 12。所以比较的是 s.c_str() + s.size() 而不是 *end == '\0'。
  • 检查 ERANGE：超出 ULLONG_MAX 的值会返回 ULLONG_MAX 并设置 ERANGE。

这些看起来是过度防御，但每一个都对应一个真实的攻击面或 bug 模式。

十四、正则缓存的悬垂引用

rg 和 find 都编译正则。重复调用同一个 pattern 时，重新编译是浪费。

十五、编译期测试

--selftest 跑一个几百项断言的测试套件，覆盖：

  • 沙箱决策（三种模式、路径穿越、符号链接、凭据文件）；
  • 注入消毒器（大小写、\r、零宽字符、全角、西里尔/希腊同形字、跨行拆分、标点连接、改写、超大输出）；
  • wrap_tool_output 的伪造抵抗；
  • read/write/write_new/edit（五种模式、歧义、部分读覆盖、no-op）；
  • rg/find/ls 语义和防护；
  • exec 超时和退出码；
  • 引用数字参数；
  • 工具注册表和政策；
  • 16 路并发只读工具调用；
  • Teamwork 作业规范化、存储往返、子代理增删、历史查询；
  • SSE 增量解析和缓冲区压缩；
  • 惰性目录遍历器；
  • 线程池作业计数；
  • 日志轮转；
  • 保管库往返和持久化；
  • 配置保存/加载/迁移/错误处理；
  • 会话分组、/new 语义、cwd 索引；
  • 加载时对 exec 结果的再消毒；
  • 中断轮次（部分回复截断、tool call 取消、原因通知、中断状态的持久化/清除）；
  • skill 发现和用量统计。

测试跑在一次性 .cell-selftest/ 目录里，结束后删除。

测试的价值不在于覆盖率数字，而在于它把设计意图写成了可执行的断言。比如"第二行 system 消息会被折叠到最前面"、"重叠匹配算作歧义"、"清除后的中断状态在重新加载后仍然清除"——这些是设计决策，不是实现细节。

结语：单文件代理的设计原则

从 cell.cpp 里能提炼出几条可推广的原则：

1. 边界要物理隔离。 只有 cell::plat 知道 OS API，只有 cell::net 知道 curl，只有 cell::encrypt 知道 libsodium。跨平台、换库、审计都变成局部问题。

2. 不要为了统一而统一。 三种 API 客户端各自处理自己的 wire format。强行抽象成公分母会在每个 API 的边界上制造 bug。

3. 服务器输入是不可信的。 流式索引有上限，SSE 缓冲区有上限，正则模式有长度和形状限制，URL 参数有大小写和编码检查。

4. 失败模式要显式。 审查失败即拒绝，中断的 tool call 直接丢弃，数字解析失败回退到默认值。"fail-closed" 不是口号，是每个分支的默认行为。

5. 持久化是状态机的核心。 会话、配置、Teamwork 存储、通知、中断状态——每一个都有明确的磁盘表示和原子写入路径。崩溃后能恢复的不只是数据，还有状态机的位置。

6. 诚实比承诺更重要。 沙箱是路径的就说路径的，不假装阻止了网络出口。README 的 Implementation notes 章节专门列出代码和文档的差异。

7. 零 token 的等待是特性。 /notices wait 阻塞在条件变量上而不是轮询 LLM，这是设计选择，不是优化。让"等待"成为一个零成本的原子操作，整个多代理编排的形态都会改变。

cell.cpp 不是最小的 AI 代理，但它可能是单位代码量里设计密度最高的之一。8000 行里没有一个函数是为了"以后可能用得上"而存在的——每一个命名空间、每一个函数、每一个防御性检查都对应一个具体的失败模式或攻击面。

这大概是单文件约束带来的最大好处：没有地方可以藏匿不必要的抽象。
